# 任務：將條列式轉換為 Markdown 表格

## 角色

你是一位專業的內容結構優化專家，專精於將散亂的條列式資訊整理成結構化的表格，讓內容更易於閱讀和比較。

## 目標

遍歷 `site/content/docs/` 下所有的 `_index.md` 檔案，分析條列式內容，將適合的條列式轉換為 Markdown 表格，提升資訊的組織性和可讀性。

## 執行步驟

1. **掃描檔案**
   - 找出 `site/content/docs/` 下所有的 `_index.md` 檔案
   - 列出待分析的檔案清單

2. **分析條列式**
   - 讀取每個 `_index.md` 的內容
   - 識別所有條列式（無序列表和有序列表）
   - 評估每個條列式是否適合轉換為表格

3. **執行轉換**
   - 將適合的條列式轉換為表格
   - 保留原有的 frontmatter（`---` 區塊）
   - 確保表格格式正確

4. **完成報告**
   - 列出已處理的檔案
   - 標註轉換的條列式數量

## 判斷標準：何時應該轉換為表格

### ✅ 適合轉換的情況

1. **鍵值對列表** - 每個項目都是「名稱：說明」的格式
   ```markdown
   # 原始條列式
   - 變數名稱：儲存資料的容器
   - 函數：可重複使用的程式碼區塊
   - 類別：物件的藍圖

   # 轉換後
   | 術語 | 說明 |
   |------|------|
   | 變數名稱 | 儲存資料的容器 |
   | 函數 | 可重複使用的程式碼區塊 |
   | 類別 | 物件的藍圖 |
   ```

2. **比較列表** - 列出多個項目的相同屬性
   ```markdown
   # 原始條列式
   - Python：易學、動態類型、廣泛應用
   - Java：企業級、靜態類型、跨平台
   - JavaScript：瀏覽器原生、事件驅動、全端開發

   # 轉換後
   | 語言 | 特性 | 類型系統 | 應用場景 |
   |------|------|----------|----------|
   | Python | 易學 | 動態類型 | 廣泛應用 |
   | Java | 企業級 | 靜態類型 | 跨平台 |
   | JavaScript | 瀏覽器原生 | 事件驅動 | 全端開發 |
   ```

3. **多屬性列表** - 每個項目包含多個結構化屬性
   ```markdown
   # 原始條列式
   - HTTP 200：成功，請求已完成
   - HTTP 404：客戶端錯誤，資源未找到
   - HTTP 500：伺服器錯誤，內部錯誤

   # 轉換後
   | 狀態碼 | 類型 | 說明 |
   |--------|------|------|
   | 200 | 成功 | 請求已完成 |
   | 404 | 客戶端錯誤 | 資源未找到 |
   | 500 | 伺服器錯誤 | 內部錯誤 |
   ```

4. **步驟與說明** - 步驟序號對應說明
   ```markdown
   # 原始條列式
   1. 規劃階段 - 定義需求和目標
   2. 設計階段 - 建立架構和介面
   3. 開發階段 - 撰寫程式碼
   4. 測試階段 - 驗證功能正確性

   # 轉換後
   | 階段 | 名稱 | 說明 |
   |------|------|------|
   | 1 | 規劃階段 | 定義需求和目標 |
   | 2 | 設計階段 | 建立架構和介面 |
   | 3 | 開發階段 | 撰寫程式碼 |
   | 4 | 測試階段 | 驗證功能正確性 |
   ```

5. **優缺點對照** - 優點和缺點的對比
   ```markdown
   # 原始條列式
   優點：
   - 速度快
   - 成本低
   - 易於維護

   缺點：
   - 功能有限
   - 擴展性差

   # 轉換後
   | 優點 | 缺點 |
   |------|------|
   | 速度快 | 功能有限 |
   | 成本低 | 擴展性差 |
   | 易於維護 | - |
   ```

### ❌ 不適合轉換的情況

1. **敘述性列表** - 每個項目是獨立的段落或完整句子
   ```markdown
   # 保持為條列式
   - 在開始專案之前，請確保您已安裝所有必要的工具和依賴項
   - 建議先閱讀官方文件，了解基本概念和最佳實踐
   - 如果遇到問題，可以查閱常見問題集或社群論壇
   ```

2. **巢狀列表** - 包含多層子項目的列表
   ```markdown
   # 保持為條列式
   - 主題一
     - 子主題 A
     - 子主題 B
   - 主題二
     - 子主題 C
   ```

3. **不規則列表** - 項目之間沒有統一的結構
   ```markdown
   # 保持為條列式
   - 記得備份資料
   - 系統需求：Windows 10 或更高版本
   - 聯繫方式請參閱官網
   ```

4. **簡短清單** - 只有 2-3 個簡單項目
   ```markdown
   # 保持為條列式
   - 是
   - 否
   ```

5. **程式碼或指令列表** - 包含程式碼片段的列表
   ```markdown
   # 保持為條列式
   - 執行 `npm install`
   - 啟動伺服器 `npm start`
   - 開啟瀏覽器訪問 `http://localhost:3000`
   ```

## 表格格式規範

1. **欄位標題**
   - 使用簡潔明確的標題
   - 第一欄通常是主要識別項目（名稱、術語、項目等）
   - 後續欄位按邏輯順序排列

2. **對齊方式**
   - 預設使用左對齊
   - 數字欄位可考慮右對齊
   ```markdown
   | 左對齊 | 置中 | 右對齊 |
   |:-------|:----:|-------:|
   | 文字   | 文字 | 123 |
   ```

3. **空值處理**
   - 使用 `-` 表示無資料
   - 不要留空（影響閱讀）

4. **內容長度**
   - 每個儲存格內容盡量簡潔
   - 過長的內容考慮保留為條列式

## 轉換範例

### 範例一：技術比較
```markdown
# 轉換前
## 前端框架比較

- React：由 Facebook 開發，使用虛擬 DOM，學習曲線中等
- Vue：漸進式框架，模板語法直觀，學習曲線較平緩
- Angular：Google 開發，完整的解決方案，學習曲線較陡峭

# 轉換後
## 前端框架比較

| 框架 | 開發者 | 特點 | 學習曲線 |
|------|--------|------|----------|
| React | Facebook | 使用虛擬 DOM | 中等 |
| Vue | 社群 | 模板語法直觀 | 較平緩 |
| Angular | Google | 完整的解決方案 | 較陡峭 |
```

### 範例二：設定選項
```markdown
# 轉換前
## 設定選項

可用的設定參數：
- `timeout`：請求超時時間，預設 30 秒
- `retries`：重試次數，預設 3 次
- `debug`：除錯模式，預設關閉
- `cache`：快取設定，預設啟用

# 轉換後
## 設定選項

可用的設定參數：

| 參數 | 說明 | 預設值 |
|------|------|--------|
| `timeout` | 請求超時時間 | 30 秒 |
| `retries` | 重試次數 | 3 次 |
| `debug` | 除錯模式 | 關閉 |
| `cache` | 快取設定 | 啟用 |
```

### 範例三：角色職責
```markdown
# 轉換前
## 團隊角色

- 產品經理（PM）：負責產品規劃、需求定義、與利害關係人溝通
- 設計師（Designer）：負責使用者體驗設計、視覺設計、原型製作
- 開發者（Developer）：負責程式碼撰寫、技術實現、程式碼審查
- 測試工程師（QA）：負責測試規劃、品質保證、缺陷追蹤

# 轉換後
## 團隊角色

| 角色 | 縮寫 | 主要職責 |
|------|------|----------|
| 產品經理 | PM | 產品規劃、需求定義、與利害關係人溝通 |
| 設計師 | Designer | 使用者體驗設計、視覺設計、原型製作 |
| 開發者 | Developer | 程式碼撰寫、技術實現、程式碼審查 |
| 測試工程師 | QA | 測試規劃、品質保證、缺陷追蹤 |
```

## 注意事項

1. **保守原則** - 如果不確定是否應該轉換，保持原狀
2. **保留上下文** - 表格前後的說明文字要保留
3. **檢查連貫性** - 確保轉換後的內容與前後文連貫
4. **保持一致性** - 同一份文件中相似的條列式應採用相同處理方式

## 開始執行

請掃描 `site/content/docs/` 資料夾，找出所有 `_index.md` 檔案，分析其中的條列式，判斷哪些適合轉換為表格，列出建議後執行轉換。
