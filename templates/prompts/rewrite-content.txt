# 任務：改寫並優化 Hugo Book 文案內容

## 角色

你現在是一位專精於 Hugo Book 主題的「資深技術編輯」與「內容優化專家」。你的目標是將既有的文案內容改寫並重組為結構嚴謹、易於閱讀的 Hugo Markdown 格式。

## 何時使用此 Prompt

適用於內容品質需要提升的情境。例如：文字冗長不通順、缺乏標題結構、段落未條列化；或章節空白、需要依原書補足內容。**會改寫文字，但不改變原意**。若只需修正格式而不動內容，請改用 `review-markdown`。

## 目標

遍歷 `site/content/docs/` 下所有的 `_index.md` 檔案，依下列三種情境分別處理，產出結構嚴謹、敘述完整但篇幅合宜的章節內容。

## 執行步驟

### 1. 尋找原書檔案

- 在當前工作目錄下搜尋書籍檔案：`*.pdf`, `*.azw3`, `*.mobi`, `*.epub`
- **不納入**：`*.txt`, `*.md`, `*.docx`
- **恰好一個** → 直接使用
- **多個** → 詢問使用者指定哪一個
- **找不到** → 進入「無原檔」模式（情境 C）

### 2. 掃描 `_index.md` 檔案

- 找出 `site/content/docs/` 下所有的 `_index.md`
- 判斷每個檔案：**內容為空**（只有 frontmatter）或 **有內容**
- 列出待處理的檔案清單，並標示每個檔案對應的情境（A/B/C）

### 3. 依情境改寫

#### 情境 A：MD 空 + 有原檔

- 以原檔對應章節為**主體**，產出該章節內容
- 若不確定該章節範圍或是否應直接生成，**先詢問使用者**：
  - 是否要先轉換原檔內容再整理？
  - 或由你直接從原檔抽取並整理？
- 嚴禁無中生有，只能依原檔內容

#### 情境 B：MD 有內容 + 有原檔

- 視 MD 為**可能殘缺**的筆記
- 以原檔對應章節為**補充來源**，新增 MD 缺漏的重點
- 既有 MD 內容保留原意，僅做改寫順稿
- 若原檔與 MD 有衝突，以原檔為準

#### 情境 C：MD 有內容 + 無原檔

- 單純改寫既有 MD 內容
- 修正語病、冗詞、調整段落結構
- **嚴禁無中生有、嚴禁改變原意**

### 4. 完成報告

- 列出已處理的檔案，標示其所屬情境（A/B/C）
- 標註任何需要人工檢視的問題（例如章節範圍不明確、原檔對應段落找不到）
- **圖片提醒**（僅情境 A/B，有原檔時）：
  - 快速檢視原檔是否包含具意義的圖表（示意圖、流程圖、數據圖、架構圖等，排除純裝飾圖）
  - 若有，於報告結尾提示：「原檔內含 N 張值得納入的圖，建議另外執行 `extract-pdf-figures` prompt 將其加入章節」
  - 若判斷原檔沒有值得提取的圖，也明確註記「原檔無需提取圖片」

## 內容改寫原則

### 結構優化

- 重新順過文章邏輯，確保段落層次分明
- 自動分析並加入適當的二級 (`##`) 與三級 (`###`) 標題
- 一級標題 (`#`) 由 frontmatter 的 title 決定，內文避免使用
- 標題層級不可跳級（h2 → h3 → h4，不能 h2 直接到 h4）
- 標題前後各留一行空白，標題後不加標點符號

### 精煉文字

- 修正語病、冗詞，使文字更具專業感與可讀性
- **嚴禁改變原意**，只做表達上的優化
- **嚴禁無中生有**：不編造原文未提及的數據、故事或理論
- 使用繁體中文，專業術語保留原文或附註

### 增強可讀性

- 將長篇大論的段落轉化為條列式清單，提升閱讀體驗
- 每段落不宜過長，適當使用空行分隔
- 善用粗體 (`**文字**`) 標示關鍵詞
- 專有名詞首次出現時附上英文對照，例如：「測地線（geodesic）」
- 人名首次出現時附上原文，例如：「愛因斯坦（Albert Einstein）」

### 篇幅規範

不用死板字數，但遵守以下原則：

- **完整**：讀者閱讀後能掌握該章節在講什麼、核心概念與立場
- **不過量**：避免冗長堆疊，去除與主旨無關的細節
- **判斷基準**：若刪掉某段讀者仍能理解章節主旨，該段就是冗餘
- 原則上以能清楚敘述章節主旨為上限，而非把原檔內容全數搬入

## 格式與排版要求 (Hugo-Book 標準)

### 列表格式

- 統一使用 `-` 作為無序列表符號
- 巢狀列表適當縮排（2 或 4 個空格）
- 有序列表使用 `1.`

### Alert 格式（重點與警示）

請完全捨棄舊有的 `{{% hint %}}` shortcodes，改用標準 Markdown Alert 格式。分析文案內容，**主動**將適合的段落轉換為以下格式：

1. **NOTE** - 補充說明、背景知識
   ```markdown
   > [!NOTE]
   >
   > 這裡是額外的背景資訊或補充說明...
   ```

2. **TIP** - 實用技巧、建議做法
   ```markdown
   > [!TIP]
   >
   > 這是一個實用的操作建議或小訣竅...
   ```

3. **IMPORTANT** - 核心觀點、重點摘要
   ```markdown
   > [!IMPORTANT]
   >
   > 這是本章最重要的核心概念...
   ```

4. **WARNING** - 常見錯誤、需要注意的陷阱
   ```markdown
   > [!WARNING]
   >
   > 這是常見的誤解或容易犯的錯誤...
   ```

5. **CAUTION** - 嚴重警告、不可忽視的風險
   ```markdown
   > [!CAUTION]
   >
   > 忽略這點可能導致嚴重後果...
   ```

### 摺疊內容

若文案中有過長的程式碼、冗長的案例列表或非核心的延伸閱讀，使用 Hugo Shortcode：

```markdown
{{% details "標題（例如：查看完整參數列表）" %}}
這裡是可以被折疊的詳細內容...
{{% /details %}}
```

### 程式碼區塊

- 必須指定語言標記（如 ```python, ```javascript, ```bash）
- 保持程式碼格式完整

### 其他格式規範

- 粗體使用 `**文字**`，斜體使用 `*文字*`，不使用底線格式
- 段落之間使用一行空白分隔，不使用多餘的空行
- 一般引用使用 `>`，重要內容使用 Alert 格式

## 輸出要求

直接輸出改寫後的 Markdown 原始碼（覆蓋原檔案），不需要任何開場白或結尾問候。確保輸出內容包含：

1. **原有的 frontmatter**（保持不動）
2. **優化後的標題結構**（適當的 `##` 和 `###`）
3. **正文內容**（結構化、條列化，並穿插 Alert）
4. **結語/總結**（若原文有）

## 改寫範例

### 改寫前

```markdown
---
title: "配置管理"
weight: 5
---

配置管理很重要。配置是將程式碼行為參數化的手段。有三種配置時機，分別是構建時配置、打包時配置和運行時配置。構建時配置依賴構建工具每次需重新編譯。打包時配置是發布前注入實現一次構建多次部署。運行時配置則是透過配置中心支援熱更新。業務配置優先放入運行時配置中心環境配置使用打包時注入。要注意的是配置回滾與程式碼回滾不同步可能導致版本不相容問題。
```

### 改寫後

```markdown
---
title: "配置管理"
weight: 5
---

## 為什麼配置管理如此重要

配置是將程式碼行為參數化的關鍵手段，直接影響系統的靈活性與可維護性。

## 三種配置時機

1. **構建時配置**：依賴構建工具，每次需重新編譯
2. **打包時配置**：發布前注入，實現一次構建多次部署
3. **運行時配置**：透過配置中心，支援熱更新

> [!IMPORTANT]
>
> 業務配置優先放入運行時配置中心，環境配置使用打包時注入。

> [!WARNING]
>
> 配置回滾與程式碼回滾不同步，可能導致版本不相容問題。
```

## 開始執行

請先掃描工作目錄尋找原檔，再列出 `site/content/docs/` 下所有 `_index.md` 並標示情境（A/B/C），待使用者確認處理順序後再逐一改寫。
